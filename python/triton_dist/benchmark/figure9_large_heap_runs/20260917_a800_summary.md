# 图 9 Triton-Distributed 大对称堆补充探测（A800，2026-09-17）

## 目的与边界

本次实验用于回答：论文图 9 中记录为 `SYM-MEM: allocation failed` 的
Triton-Distributed GEMM--ReduceScatter / GEMM--AllReduce 路径，在提高
NVSHMEM 对称堆预算后能否运行，以及其探索性 speedup 是多少。

- 设备：单机 4 × NVIDIA A800-SXM4-80GB，NVLink（GPU 间均为 NV8）。
- 数据类型：BF16。
- 对称堆预算：`NVSHMEM_SYMMETRIC_SIZE=8589934592`，即 8 GiB/PE。
- 仓库启动器默认值：`1000000000` 字节，即约 0.931 GiB/PE。
- 计时：单次程序启动，5 次 warmup、10 次测量。
- 所有下列成功计时均通过逐 rank 数值检查。
- 这是 A800 上的探索性补充结果，不是论文图 9 的 A100 历史结果，不能直接替换图 9。

## GEMM--AllReduce 结果

原 benchmark 固定使用 `BLOCK_SIZE_N=256`。两个 `N=29568` 的形状在扩大对称堆
后不再发生 allocation failure，但会进一步触发 `N % BLOCK_SIZE_N == 0` 断言。
因此仅在 benchmark 层增加了可选 `--block_size_n` 参数，未修改内核；使用
`--row_wise --block_size_n 128` 后，四个形状均通过正确性检查。

下表比较 16 与 32 个通信 SM。每行“较好值”仅表示这两个候选中的较好单次结果，
不是完整 autotune 结果。

| 形状 `(M,N,K)` | 16 comm SM | 32 comm SM | 两者较好值 |
|---:|---:|---:|---:|
| `(8192,29568,8192)` | 0.6373× | 0.7909× | 0.7909× |
| `(8192,49152,12288)` | 0.7415× | 0.8591× | 0.8591× |
| `(8192,53248,16384)` | 0.8405× | 0.7816× | 0.8405× |
| `(16384,29568,8192)` | 0.6353× | 0.7890× | 0.7890× |

代表形状 `(8192,49152,12288)` 还测试了 64 个通信 SM，speedup 为约 0.535×；
由于留给 GEMM 的 SM 过少，性能明显下降。该形状在默认 tile-wise、
`BLOCK_SIZE_N=256`、16 个通信 SM 下虽然正确，但只得到约 0.0408×；改为 row-wise
后为约 0.7239×，说明 AR 结果对 tile 映射和 SM 划分非常敏感。

## 运行环境模板

```bash
export CUDA_VISIBLE_DEVICES=0,1,2,3
export NVSHMEM_SYMMETRIC_SIZE=8589934592
export NVSHMEM_DISABLE_CUDA_VMM=1
export NVSHMEM_HOME=/root/miniconda3/lib/python3.12/site-packages/nvidia/nvshmem
export LD_LIBRARY_PATH="$NVSHMEM_HOME/lib:/usr/local/cuda/lib64:${LD_LIBRARY_PATH:-}"
export CUDA_DEVICE_MAX_CONNECTIONS=1
```

RS 示例：

```bash
torchrun --standalone --nproc_per_node=4 \
  benchmark/benchmark_gemm_reducescatter.py \
  --M 8192 --N 49152 --K 12288 \
  --dtype bfloat16 --mode all --warmup_iters 5 --iters 10
```

AR 示例：

```bash
torchrun --standalone --nproc_per_node=4 \
  benchmark/benchmark_gemm_allreduce.py \
  --M 8192 --N 49152 --K 12288 \
  --dtype bfloat16 --warmup_iters 5 --iters 10 \
  --row_wise --block_size_n 128 --num_comm_sms 32
```

## 解释限制

1. 提高对称堆只解除容量约束，不会自动改善算法性能。
2. 当前结果来自 A800；论文图 9 标注为 A100，平台不可混用。
3. 当前是单次启动的探索性数据。若要写入论文，应固定参数后进行至少 3 次独立启动，
   以 rank-max 延迟计算每次 speedup，再报告中位数与最小--最大范围。
4. AR 在当前 A800 上即使解除分配失败并进行小范围参数选择，仍慢于 Torch/NCCL；
   不能把“可分配”写成“性能可竞争”。
