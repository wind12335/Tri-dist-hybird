• 这个脚本的核心作用可以概括成一句话：

  它在 “不做重叠、串行执行” 的前提下，测量几类典型张量并行算子链里，计算时间 和 通信时间 各占多少，为你论文里“为什么要做计算与通信重叠”提供一组动机性数据和图。主文件是
  bench_intro_tp_comm_breakdown.py。

  更准确地说，它不是在测“你的重叠优化有多大收益”，而是在测一个 串行 baseline：如果把通信和计算拆开来看，通信到底占了多少比例。这个结果很适合放在 introduction 或 motivation 部分，因为它先证
  明一个事实：在代表性 TP operator chain 中，通信并不小，因而存在做 overlap 的必要性。

  整体逻辑
  脚本先从命令行读取实验参数，包括 M、dtype、测试轮数、要测的模型和算子模式等，见 bench_intro_tp_comm_breakdown.py:56。其中默认测试 3 个模型：Qwen2-72B、GPT-3-175B、LLaMA-3.1-405B，这些模
  型的层维度来自 /data/coding/Triton-distributed/python/triton_dist/test/utils.py:31。这里的 K 和 N 本质上就是线性层乘法里常见的 hidden/intermediate 维度，M 默认是 8192，可以理解为展平后的
  token 数或 batch-seq 维度。

  随后脚本初始化分布式环境，设置当前 GPU，遍历每个 pattern × model 组合，在每种组合下分别测三种时间：

  1. serial_total_ms：完整串行链路的总时间。
  2. compute_only_ms：只保留 GEMM 计算，不做通信。
  3. comm_only_ms：只保留通信，不做 GEMM。

  最后它把结果汇总成 CSV，并且可以画柱状图，见 bench_intro_tp_comm_breakdown.py:324 和 bench_intro_tp_comm_breakdown.py:349。

  它测的三类 TP 模式是什么
  脚本定义了 3 种代表性模式，见 bench_intro_tp_comm_breakdown.py:43：

  1. ag_gemm：AllGather + GEMM
  2. gemm_rs：GEMM + ReduceScatter
  3. gemm_ar：GEMM + AllReduce

  这三类模式基本覆盖了分布式大模型里常见的“先通信再算”或“先算再通信”的 TP 链路。

  对应实现分别在：

  - bench_intro_tp_comm_breakdown.py:166
  - bench_intro_tp_comm_breakdown.py:186
  - bench_intro_tp_comm_breakdown.py:208

  你可以这样理解它们：

  ag_gemm
  每个 rank 先持有一部分输入 a_shard，通过 all_gather 拼成完整输入 a_full，再和本地权重分块做 GEMM。也就是先补齐输入，再计算输出分片。

  gemm_rs
  每个 rank 先用本地分块做部分 GEMM，得到 partial，然后通过 reduce_scatter 把规约后的结果分发到各个 rank。也就是先算部分结果，再做规约+切分。

  gemm_ar
  每个 rank 先算本地 partial output，再对输出做 all_reduce。这种模式适合表达“局部算完后，需要全局求和”的场景。

  计时是怎么做的
  计时核心在 bench_intro_tp_comm_breakdown.py:109 和 bench_intro_tp_comm_breakdown.py:114。

  sync_all(pg) 做了两件事：

  - torch.cuda.synchronize()，保证当前 GPU 上之前的 kernel 都完成。
  - torch.distributed.barrier(...)，保证所有 rank 对齐到同一个时间点。

  perf_func_lockstep(...) 的思路是：

  - 先 warmup 若干次，避免第一次启动开销污染结果。
  - 正式计时时，每轮都在执行前后做一次全局同步。
  - 用 CUDA Event 记录每轮开始和结束。
  - 最后对多轮结果取平均。

  这意味着这个脚本测的是一种 lockstep、严格对齐的 rank 级平均耗时。对于论文来说，这样的口径很稳，因为它尽量消除了不同 rank 起跑不一致带来的偏差。

  三个 measure_* 函数在做什么
  这部分是整个脚本最关键的地方：

  - bench_intro_tp_comm_breakdown.py:214
  - bench_intro_tp_comm_breakdown.py:240
  - bench_intro_tp_comm_breakdown.py:265

  每个函数都定义了三个闭包：

  _serial_total()
  执行完整链路，比如 AllGather + GEMM 或 GEMM + ReduceScatter。这是“真实串行基线”。

  _compute_only()
  只执行 GEMM，不做通信。目的是测“纯计算部分”的时间。

  _comm_only()
  把计算结果预先准备好，只执行通信。目的是测“纯通信部分”的时间。

  比如在 measure_gemm_rs() 里：

  - _serial_total() 是先 matmul 再 reduce_scatter
  - _compute_only() 只做 matmul
  - _comm_only() 直接对预先算好的 partial 做 reduce_scatter

  这个设计很适合做论文图，因为你能把总链路拆成两个组成部分去解释，而不是只给出一个黑盒总时延。

  另外，每次正式测量前都调用了 wait_until_max_gpu_clock_or_warning(...)，见 bench_intro_tp_comm_breakdown.py:231。这说明作者在尽量减少 GPU 动态频率带来的波动，让 benchmark 更稳定。

  结果是怎么汇总的
  每个 rank 都会得到自己的本地时间，然后通过 bench_intro_tp_comm_breakdown.py:134 的 aggregate_metric() 做跨 rank 聚合，得到：

  - mean
  - max
  - min

  其中真正被后续绘图和分析主要使用的是 mean，max 也被保存到了 CSV 里，便于你后续分析不同 rank 的不均衡程度。

  主循环在 bench_intro_tp_comm_breakdown.py:427。对每个 pattern × model，它会生成一个 record，里面最重要的有四组量：

  - serial_total_ms_mean
  - compute_only_ms_mean
  - comm_only_ms_mean
  - 两类 share 指标

  这里的 share 有两种，区别很重要：

  component_compute_share / component_comm_share
  公式是：

  - compute_only / (compute_only + comm_only)
  - comm_only / (compute_only + comm_only)

  这两个 share 加起来正好是 1。它们反映的是：如果只看“纯计算时间”和“纯通信时间”这两个组件，谁占比更大。
  这个指标特别适合画堆叠柱状图。

  serial_compute_share / serial_comm_share
  公式是：

  - compute_only / serial_total
  - comm_only / serial_total

  这反映的是：纯计算时间、纯通信时间，相对于真实串行总时延分别占多大比例。
  它们不一定加起来等于 1，因为真实总时间和“纯算 + 纯通信”的测法不是同一次执行，也会受到缓存、kernel 调度、同步等因素影响。

  作图部分的意义
  作图函数在 bench_intro_tp_comm_breakdown.py:349。

  它做的是一个非常典型的 motivation 图：

  - 横轴是模型
  - 每个子图对应一个 TP pattern
  - 柱状图堆叠显示计算占比和通信占比
  - 柱子上方再标出该模式的 serial_total_ms_mean

  也就是说，一张图同时告诉读者两件事：

  1. 总延迟有多大
  2. 其中通信占了多少

  这很适合你写 introduction 时的叙述逻辑：
  “随着模型规模增大，代表性 TP operator chain 的串行时延显著上升；在多个模型配置下，通信已占据不可忽略甚至主导的比例，因此计算与通信重叠具有必要性。”
